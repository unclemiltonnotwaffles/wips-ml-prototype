1. The Problem

A deauthentication flood is a trivial denial-of-service attack on 802.11: an attacker spoofs management frames to force every client off the network. It needs no password and no special hardware.

This project builds a transparent end-to-end prototype: capture → features → ML → alert → block, using a Random Forest classifier.

3. Features (why these 11?)

Each window becomes one row. Ratios (not just counts) make the model shape-aware — a busy legitimate AP sends hundreds of frames/s too.

5. The "P" in WIPS

When a window is classified attack, the detector raises an alert and increments a strike counter for that MAC. After 2 strikes, the MAC is written to a persistent blocklist.

t=3s normal traffic
t=47s ⚠ ALERT aa:bb:..:02 p=0.98
t=48s ⚠ ALERT aa:bb:..:02 p=0.97
t=48s 🛡 BLOCK aa:bb:..:02

Why two strikes? One alert could be a false positive; two consecutive attacking windows from the same MAC is a very strong signal.

Safety: DRY_RUN=True by default. On an authorised lab host, _apply_block() runs iptables -I INPUT -m mac --mac-source <mac> -j DROP.

6. Reproducibility

  • Random Forest, 100 trees, max depth 12, class_weight="balanced".
  • Time-ordered 70/30 split — no attack episode appears in both halves.
  • Fixed seeds (RANDOM_STATE=42).
  • Tests: python tests/test_features.py.
  • Dataset-agnostic: same pipeline runs on AWID3 or synthetic traffic.
  • Dataset: AWID3-CSV (Kaggle) / Official AWID3.

7. Limitations & Future Work

Limitations

  • Strong signal in deauth_count; other attacks need re-training.
  • Each window is scored independently.
  • Offline — reads CSVs; live capture needs a monitor-mode NIC.

Would improve

  • Rolling 5 s features to smooth isolated false positives.
  • CalibratedClassifierCV for trustworthy probabilities.
  • Adversarial validation on disassoc / rogue-AP.
  • Active deauth back to the attacker (injection).
  • Streaming learner for concept drift.
